### 2. Regex + whole-word find (~1.5 hrs)

Single pure-function extension, benefits every find caller (edit/view/PDF + folder search).

**`src/lib/editor-logic.js:250` `findMatches`** — extend signature:
```js
export function findMatches(text, query, { caseSensitive = false, regex = false, wholeWord = false } = {}) {
  if (!query) return [];
  if (regex) {
    // Compile with try/catch; on invalid regex return [] (UI shows "no match").
    let re;
    try { re = new RegExp(query, caseSensitive ? 'g' : 'gi'); }
    catch { return []; }
    const out = [];
    let m;
    while ((m = re.exec(text)) !== null) {
      // Guard against zero-length matches (e.g. `a*`) — advance by 1.
      const len = m[0].length || 1;
      out.push({ start: m.index, end: m.index + (m[0].length || 0) });
      if (m[0].length === 0) re.lastIndex++;
    }
    return out;
  }
  // Existing substring path, with optional wholeWord wrap.
  ...
}
```

### 4. Custom CSS injection (~45 min)

Power-user escape hatch. One textarea in Settings → injects a `<style>` applied to both editor preview and reader.

**`index.html` Settings → Appearance** (after the theme grid ~line 657) — add a `<textarea id="settings-user-css" placeholder="/* Your custom CSS, applied to rendered Markdown */">` with a Save button. Mirror the existing settings-row pattern.

**`src/main.js`** — `applyUserCss()` helper: writes `<style id="mdpeek-user-css">` into `<head>` (or replaces if present) from `localStorage.getItem('mdpeek-user-css')`. Called on init + on settings change. The style targets `.markdown-body` selectors so it applies uniformly to view-mode article, edit-mode preview, reader article, and slideshow slides (all share `.markdown-body`).

**Settings wiring** — add `'mdpeek-user-css'` to `SETTING_KEYS` (reset list), sync the textarea value in `syncSettingsControls`, debounce-save on input (don't save every keystroke — 300ms).

**Safety** — the CSS is scoped to `.markdown-body` by convention (we document this in the placeholder), not enforced. DOMPurify doesn't touch `<style>` tags we insert programmatically into `<head>` (it only sanitizes rendered markdown HTML). No XSS risk because user CSS can't execute JS.

## Risk
Medium — the autocomplete is the riskiest piece (caret positioning + non-focusable overlay + key interception on the textarea). Mitigations:
- Pure helpers (`detectTrigger`, `buildCandidates`, `acceptSuggestion`) are fully unit-tested before any DOM wiring.
- The dropdown is non-focusable and only intercepts Tab/Arrow/Enter; Esc and any other key fall through, so a bug in the dropdown can never trap the user.
- A `localStorage` kill-switch (`mdpeek-autocomplete` = `0`) disables the whole feature if it misbehaves in production — same pattern as the other feature flags.
- `findMatches` extension is backward-compatible by construction (positional arg still works); all 468 existing tests prove no regression.
- Reader TOC and custom CSS are pure additions with no behavior change.
